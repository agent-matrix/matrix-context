# From Mixture of Agents to Mixture of Contexts

There is a small idea I keep returning to, and it has followed me from the inside of neural networks all the way out to the architecture of whole systems. The idea is sparse routing: if you want more capability, do not make one thing bigger and run all of it every time. Build many specialists and learn to call only the few that a given moment needs. Inside a model this is mixture of experts, and it is how a network can hold an enormous amount of capacity while spending only a fraction of it per token. In an earlier essay I argued that the same principle does not stop at the layer boundary — that it scales upward, from experts inside a model to a mixture of models, and then to a mixture of agents. This piece is about taking that same idea one step further down, into the thing every agent is starving for and drowning in at the same time: context.

Anyone who has built an assistant that is supposed to remember things knows the shape of the problem. You take the conversation history, the user's preferences, the documents, the decisions, the rules, and you put them in a vector store, and you retrieve the nearest matches into the prompt. It demos beautifully. Then it meets production and it falls apart in slow motion. The prompt grows until the model loses the fact you actually needed somewhere in the middle of it. The bill grows because you are shipping tens of thousands of tokens of history to get back a sentence. And worst of all, the system has no opinion about what it is doing. To a flat index, a user's stable preference and an offhand remark from a chat three weeks ago and a compliance rule and a paragraph of a manual all look like the same thing: a chunk, ranked by how closely its words resemble the query. When the budget is tight — and it is always tight — similarity is a bad proxy for usefulness.

So I asked the obvious question. If routing is the right answer for experts inside a model, why are we still treating memory like one undifferentiated pile? What if the memory store were a set of context experts — a place for who the user is, a place for what was decided, a place for what happened and when, a place for the rules — and a router chose only the relevant few for each query, the same way a mixture-of-experts gate chooses which subnetworks to fire? I called the result Matrix Context, and the technique Mixture of Contexts. The product is small on purpose: it routes a query to a handful of typed experts, retrieves inside them with a hybrid of keyword and vector search, and then composes a context pack that fits a token budget — choosing items not by nearness alone but by a blend of relevance, how important the item is, how recent it is, and how much it duplicates what is already in the pack. And it can tell you, for any query, exactly which experts fired, which items it kept, and why it dropped the rest.

I want to be honest about what this is and is not, because I have watched too many projects sell a metaphor as if it were a discovery. These context experts are not learned mixture-of-experts modules with trained gates. They are typed partitions, and the router is a policy that runs at retrieval time, not a network shaped by gradients. The mechanism sits in a real and active line of research — routing queries to clustered document experts, deciding whether to retrieve at all, routing across specialized retrievers — and that is a comfortable place to stand, not a weakness. The thing I am actually contributing is not a new training objective. It is a shape: typed memory, an explicit routing decision, a budgeted composition, and the insistence that every choice be inspectable.

Then I did the part that I think separates engineering from storytelling. I built the engine and I benchmarked it against ordinary flat retrieval, and I let the benchmark tell me the truth instead of the other way around. The first result was not flattering, and I am glad it was not. Running with the lightweight, offline, no-download embedder that ships as the default, my clever routing did not beat flat retrieval. It tied it. The reason was plain once I looked: a hashing embedder cannot really tell the policy partition from the chat partition, so the router, sensibly, refused to commit and widened its net — and a wide net catches the same noise that flat retrieval catches. The routing bought nothing, because routing is only as good as the signal it routes on.

That sounds like a failure. It is the most useful thing the benchmark told me. Because when I gave the router a competent signal — the kind a real embedding model provides — the same engine matched flat retrieval's recall while cutting the distracting, off-topic content in the prompt by around sixty percent and using roughly half the tokens to do it. That is the whole value, stated precisely: not better answers, but the same answers in far less context, with every selection explainable. And the entire payoff is gated on one thing, embedding and routing quality. Everything else — the storage, the server, the integrations — is the safe part of the system. The risky part, the part that decides whether any of this is worth building, is the router and the model behind it. So that is what gets built and proven first. I find this clarifying. It is easy to spend months on the plumbing that you know how to write and never test the assumption the whole product rests on.

What happens next is where it gets interesting for the rest of my work, because Matrix Context was never meant to live alone. The first real test is agent-generator: when you generate an agent and ask for persistent, governed memory, it should hand you a project that already remembers and recalls across turns, with Matrix Context wired in and a local store underneath, not a library you still have to learn. If a generated agent cannot accumulate and use memory out of the box, the integration is not finished. The deeper one is HomePilot, my local-first home assistant, which already taught me most of what I believe about memory — keep the profile separate from what is learned, offer a deterministic mode and an adaptive mode, and keep what you inject into the prompt small. The plan there is not to replace what works but to let HomePilot treat Matrix Context as an externalized, inspectable context plane it can hand to other agents or reach over a standard protocol. That integration is also how the synthetic benchmark becomes a real one, because a working assistant gives you real queries and real answers about whether it recalled the right thing.

The throughline, from experts to agents to context, is the same sentence I started with. Capability does not come from running everything all the time. It comes from having many specialists and the judgment to call only the ones you need — and, I would now add, the honesty to show your work. An agent that can tell you why it remembered what it remembered is worth more than one that simply remembers more. That is the layer I am building, and the benchmark, including the part that did not flatter me, is why I think it is worth building at all.
